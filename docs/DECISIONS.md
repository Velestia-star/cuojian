# 设计决策记录

这份文件记录「为什么这么做」，避免三个月后自己推翻自己。格式参考 ADR：背景 → 决定 → 代价。

## D1 出题用队列模型 A（流式队列），不用每次随机抽题

- **背景**：需求要求「答错的题排到后方」「刚答完的题不会立刻再出现」「退出要能接着刷」。每次随机抽题无法同时满足这三条，且不可测试。
- **决定**：开轮时整池 Fisher–Yates 打乱一次，`pending[0]` 永远是当前题；作答后按冷却 + 尾部窗口重插回队列。队列落库，重进接着刷。
- **代价**：A 模型没有天然终点，所以补了三条终止线：队列空、用户点「结束本轮」、单轮 50 题上限（R13）。
- **不选 B 模型**（轮次快照）：B 的「本轮每题最多一次」会让刚答错的题本轮见不到，和 R5 的直觉冲突。

## D2 选择题答案只存选项 id

- **背景**：洗牌后字母会变。若把答案存成 "B"，打乱即错乱；若存选项文本，选项文本重复时判错。
- **决定**：`option.isCorrect` 是唯一真相，判分用 `correctOptionIds` 集合；字母是渲染产物（`optionLetters`），任何地方都不持久化。
- **代价**：解析里不能写「选 A」，录入页的提示与 README 都要求写成结论。

## D3 星数永不参与调度

- **背景**：R9/I5 要求星数不影响出题顺序，避免「加权抽题」把调度调参搅成一锅粥。
- **决定**：`pickNext(pending)` 的签名里只有队列；`reinsert` 只看队列长度与配置。`stars` 只出现在展示层与 `card` 表。
- **验证**：`scheduler.test.ts` 用 fast-check 断言同种子下不同 stars 得到完全相同的队列。

## D4 随机与时间全部注入

- **背景**：调度是「随机 + 状态」叠加，不可复现就等于不可测。
- **决定**：`Rng` 由 mulberry32 提供，`now` 是 `() => number`；只有 `src/app/deps.ts` 这个组合根读 `Date.now()`。测试用固定种子 + 假时钟。
- **代价**：多一层依赖传递，但换来「bug 可复现」和属性测试的可能性。

## D5 判定规则版本化（graderVersion 写进 attempt）

- **背景**：填空归一化规则以后一定会调（尤其「宽松」边界），不能让历史结论被新规则追溯改写。
- **决定**：`attempt.graderVersion` 记录当时的规则版本；`GRADER_VERSION` 在 store 里集中维护，改规则先 +1 再改实现。
- **代价**：v0.1 没有「按旧规则重算」界面，只保证数据留存。

## D6 Repository 接口隔离存储

- **背景**：v0.1 用 Dexie（IndexedDB），未来 Capacitor 里要换 SQLite。
- **决定**：业务与组件只依赖 `Repository` 接口；Dexie 与内存两份实现共享同一套行类型与语义。组件禁止直接 `import dexie`。
- **代价**：多写一层转发；换来换存储时只改一个文件。

## D7 路由用 HashRouter + `base: './'`

- **背景**：GitHub Pages 是静态托管，`BrowserRouter` 刷新子路由会 404。v0.1 不想引入 Pages 的 404 回退配置。
- **决定**：HashRouter，构建 `base: './'`，产物丢进任意子路径都能跑。
- **代价**：URL 带 `#`，可接受。

## D8 v0.1 不做导入导出，但把它列为 v0.2 第一优先级

- **背景**：浏览器清缓存 / 换设备 = 数据消失，这是本地优先产品的头号风险。
- **决定**：先把闭环跑通；`attempt` 与 `card` 的数据结构已经完整，导出只需序列化 9 张表。
- **代价**：v0.1 只适合自己日常用，发布给陌生人前必须先补备份。
